# Decisions and defaults

Every default or deviation from the original build specification, and why.

| # | Decision | Why |
|---|---|---|
| 1 | **PayPal Orders v2 (sandbox) replaces the Razorpay placeholder.** Approved supplier orders can be paid with PayPal (`/payments/orders/:id/create` and `/capture`). Without `PAYPAL_CLIENT_ID/SECRET` the same flow runs in a clearly labelled *simulated* mode. | The hackathon judges how well the project uses the PayPal Developer Platform. Payment is the natural end of the purchasing loop. |
| 2 | Amounts are converted INR → `PAYPAL_CURRENCY` (default USD at `PAYPAL_FX_INR_TO_CURRENCY=0.012`) at checkout. | PayPal sandbox accounts outside India cannot settle INR domestic payments. The rate is configurable and shown in the UI. |
| 3 | Capture is verified server-side: the PayPal order id must match the one created for that purchase order, and `reference_id` must equal our order id. | Stops a client from marking an order paid with someone else's PayPal order. |
| 4 | Payee: if a supplier has `paypalEmail`, the PayPal order names that payee; otherwise the platform's sandbox merchant receives the funds. Seeded suppliers have no PayPal email. | Fictional emails would fail in the real sandbox. |
| 5 | **The intelligence logic is implemented in Node.js** (`server/src/intelligence/*`) instead of a separate Python/FastAPI service. | One runtime means judges can run everything with `npm run setup && npm run dev`. The algorithms match the spec: Holt-Winters damped additive with m=12, Holt damped, mean-of-3, naive backtest, 3-MAD clipping, anchor rescaling, the scoring formula and the mandi verification rule. Each one is unit tested. |
| 6 | Holt-Winters / Holt smoothing parameters come from a small grid search that minimises in-sample one-step SSE (φ = 0.98). | Same idea as statsmodels' optimiser, with no numerical-solver dependency. |
| 7 | The backtest trains the same method family the full history selects (24+ months → Holt-Winters on 21 months, with the trend initialised from a partial second season). | Otherwise every seasonal product was backtested with a non-seasonal model and unfairly lost to naive. |
| 8 | σ_daily = σ_monthly / √30. | Spec approximation: it assumes independent days and is documented in `inventoryQuantities`. |
| 9 | **Zero-token agent mode.** With no `GROQ_API_KEY` (or with `AGENT_USE_LLM=false`) the agent uses a deterministic *rules planner* that calls the **same tools with the same code-enforced rules**. With a key, the LLM plans with function calling (25 steps, 60 s). If the LLM fails mid-run, the run falls back to the rules planner (`mode: llm→rules`). | Efficiency: routine carts need no LLM. the LLM adds judgement and natural-language reasons when it is enabled. Safety never depends on the planner. |
| 10 | **LLM provider: Groq free tier, models `openai/gpt-oss-120b` (function-calling agent) and `openai/gpt-oss-20b` (extraction, separate per-model rate limit)** — the Llama chat models are no longer offered to this key (checked via `GET /models`) (OpenAI-compatible Chat Completions via plain `fetch`, no SDK). Free-tier tokens-per-minute limits shape the agent design: a `get_reorder_candidates` tool (15 most urgent items with their allowed qty range) replaces per-product forecast calls; a batched `add_cart_items` tool lets the model propose the whole cart in one call (each item is still validated and logged as its own `add_cart_item` step); executed batch arguments and old per-item results are collapsed in the history; 429s honour `Retry-After`; LLM runs may take up to 150 s (spec: 60 s). Information-only price notices the model skips are added deterministically afterwards. First-boot seeding uses the rules planner; *Refresh suggestions* runs the LLM. Verified live on all three demo shops: 0 rejected calls, 0 rule violations. | Zero cost for the team and judges, within free-tier limits. |
| 11 | One combined extraction call per article returns both trend fields and price-signal fields. | Halves LLM calls compared with separate trend and price classifiers. |
| 12 | Category tagging and keyword canonicalisation try free deterministic steps first (taxonomy keyword match, alias table, Levenshtein ratio ≥ 90). The LLM runs only when those fail and LLM mode is on. | Token efficiency; it also makes fixture mode fully deterministic. |
| 13 | LLM fixtures are keyed by `sha256(task + stable input id)` (for example the article URL) instead of the full prompt text. | Prompt wording can change without invalidating recorded fixtures. |
| 14 | Supply-chain inference without an LLM orders the scopes reported by the articles (global → national → regional → local) and cites article ids. It is always labelled `inferred`, capped at 0.6 confidence, and fails closed (empty) on validation errors or unknown ids. | Gives explainable output offline and never presents inference as fact. |
| 15 | Price-alert product matching uses product **names** (with Hindi/Marathi synonyms), not categories. | Category matching linked a plywood signal to hinges and drawer channels. |
| 16 | Perishables may appear in the Prices cart only as `kind: info` with quantity 0 (a warning). Any buy quantity is rejected in code. | The spec says "perishables show warning only". |
| 17 | One open cart item per (vendor, cart, product or keyword), enforced in code and by a partial unique index. A second alert for the same product updates that item. | Spec duplicate rule. The Alerts page still lists every alert. |
| 18 | The social-item quantity is always the system's trial quantity. Vendors can approve or dismiss but cannot change it. | Keeps the trend experiment small and comparable for crossover tracking. |
| 19 | No `MONGODB_URI` → in-memory MongoDB replica set (transactions work), auto-seeded on boot. | Zero-setup demo. Docker Compose and Atlas use a real replica set. |
| 20 | The seed starts history on the 1st of a month and includes 2 historical trend outcomes for the grocery demo shop (labelled demo data). | Complete first months keep forecasts honest. The crossover panel needs evaluated outcomes, which otherwise take 30 days to appear. |
| 21 | Demo accounts cannot be deleted, and `/auth/demo` logs into them without a password. | Keeps a shared hosted demo usable for judges. |
| 22 | Google Trends: there is no official API and pytrends is unofficial. Real mode reads an optional `TRENDS_PROXY_URL` (a pytrends sidecar). Without it, search growth falls back to neutral (1.0) and the job finishes with partial data. | The spec says to expect breakage and allow partial results. |
| 23 | Tests use the built-in `node:test` runner with supertest and mongodb-memory-server instead of Jest. | Native ES-module support with no experimental flags or extra dependencies. |
| 24 | Dependencies: express 4.22.3, mongoose 8.24.7, nodemailer 10.2.1, zod 4.6.7 and node-cron 4.6.0 were chosen to clear every `npm audit` advisory, and each was published more than 14 days before the build. | Spec security rules: audit clean, and releases at least 14 days old. |
| 25 | Licence: MIT. | The hackathon requires an open-source licence file. The human owner may change it. |
| 26 | Fixture articles use fictional outlets, people and `fixtures.palprocure.dev` URLs. | Avoids putting invented quotes in the mouths of real publications or celebrities. |
| 27 | **Two injection layers on incoming article text.** (1) Llama Prompt Guard 2 (86M) scores each new article; ≥ 0.5 → quarantined, never extracted. (2) Code, not the model's label, decides article kind: a price story's commodity is removed from its trend products. | Live test: the extractor obeyed an embedded "output kind=trend"; Prompt Guard caught classic injections (0.92–0.97) but missed a "SYSTEM OVERRIDE" variant (0.001), so neither layer alone is enough. Purchase rules are enforced in code regardless. |
